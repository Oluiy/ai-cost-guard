Render, Heroku, and Railway

Docker is not required on any of these three. Each also has a native runtime path that builds straight from your repo's Go source, no Dockerfile involved. Pick whichever your platform dashboard offers; both end up running the same binary the same way.

Shared setup

  1. Deploy the published image, ghcr.io/oluiy/fitguard (multi-arch, built from the same binary as each GitHub release). There is nothing to compile on the platform: no Go toolchain, no Build Command, no build minutes. Pin a version tag such as ghcr.io/oluiy/fitguard:0.1.3 for production, or use :latest to follow releases.
  2. Generate that YAML first, on your own machine: fitguard init --config config.production.yaml. It's interactive (masked password, provider keys, budgets) — there's no non-interactive/scripted form of it, so this step can't run as part of a platform's build/deploy hook.
  3. Set FITGUARD_CONFIG to the complete production YAML just generated, pasted as one multi-line environment variable. See What goes where if you haven't yet. Reference secrets as ${OPENAI_API_KEY} inside it, then add those secrets separately as their own env vars in the platform settings.
  4. Set port: ${PORT} in the YAML and configure the platform health check as /healthz.
  5. Use one instance first. Add Redis before adding replicas.

Postgres instead of a disk

A platform without a persistent disk (Heroku, Render free, any autoscaled setup) can keep everything in Postgres instead: request history, and also the settings you change in the dashboard (budgets, keys, the dashboard login). Add this to the YAML and set DATABASE_URL as a platform secret: 

storage:
  backend: postgres
  postgres_url: ${DATABASE_URL}

On first boot the settings in your YAML are copied into the database once; after that the database wins, so a redeploy from the same YAML does not undo dashboard edits. Several instances share the same settings and pick up each other's changes within about 30 seconds. Reset a forgotten dashboard password with fitguard reset-dashboard-password run anywhere that has the same YAML and DATABASE_URL. With the default SQLite backend you can get the same behaviour with storage: {state: database}.

Already have history in SQLite? Copy it across once, before the first start on Postgres: fitguard import-history --from ./data/fitguard.db --config config.production.yaml. Every row keeps its original timestamp, the SQLite file is only read, and it refuses to run into a database that already has history so a second run can't double-count it.

Render

The repo's render.yaml is a Blueprint that deploys the image with a health check and a persistent disk already set up. After running fitguard init on your machine (set port: ${PORT} and data_dir: /data in the generated file), go to New → Blueprint in the Render dashboard and pick this repository. Render asks for FITGUARD_CONFIG (paste the whole file) and your provider keys once, and keeps them out of git.

To set it up by hand instead: New → Web Service → Existing Image, enter ghcr.io/oluiy/fitguard:latest, add the same environment variables, set the health check path to /healthz, and add a disk mounted at /data.

A disk needs a paid plan. Render's free tier has no persistent disks, so request history can't survive there, and free services spin down after 15 minutes idle and take about a minute to wake. For a proxy in front of every AI call, that cold start lands on a user. The Blueprint uses starter. A disk is single-instance and disables zero-downtime deploys, so don't scale this service horizontally with it attached.
This is FitGuard's own service, separate from any app you already run on Render. Leave your existing service's build and start commands exactly as they are. Add FitGuard as its own service, take the URL Render gives it, and set that as FITGUARD_URL on your existing service. See using FitGuard alongside an existing Dockerfile for the same idea.

Building from source still works (choose the Go environment with go build -o fitguard ./cmd/fitguard and start command ./fitguard run), but the image is simpler and is the tested path.

Fly.io

The cheapest durable option here: the smallest always-on machine is about $2.19 a month and a volume is $0.15 per GB, so roughly $2.30 all in. The repo's fly.toml already points at the image, mounts a volume at /data, and keeps the machine running (a stopped machine would cold-start on a user request). 

fitguard init --config config.production.yaml   # set data_dir: /data and port: 8787
fly launch --no-deploy --copy-config --name your-app-name
fly volumes create fitguard_data --size 1 --region iad
fly secrets set FITGUARD_CONFIG="$(cat config.production.yaml)" OPENAI_API_KEY=sk-...
fly deploy

Fly's managed Postgres starts at $38 a month, which is why a volume is the better fit while FitGuard stores history in SQLite. A volume attaches to one machine, so keep it at one.

Heroku

Heroku dyno filesystems are ephemeral, so do not use Heroku for durable SQLite history. Add Heroku Key-Value Store or another TLS Redis service for shared budget state. The entry-level KVS plan is not persistent, so use a production plan when Redis durability matters.

Heroku's container path (below) is the one documented here in full; a classic Go buildpack path also exists on Heroku if you'd rather not use Docker, but isn't covered step-by-step in this guide.

Generate that config file first — fitguard init is interactive (masked password, provider keys, budgets) and has no non-interactive/scripted form, so it runs on your own machine, not on Heroku:

fitguard init --config config.production.yaml
heroku login
heroku create fitguard-prod --stack container
# config.production.yaml here is just a local file on your machine — name it
# anything, it's never committed (see "What goes where" on the overview page):
heroku config:set -a fitguard-prod \
  FITGUARD_CONFIG="$(cat config.production.yaml)" \
  OPENAI_API_KEY="..."
heroku addons:create heroku-redis:mini -a fitguard-prod
heroku container:login
# Build on Apple Silicon for Heroku's x86_64 container runtime:
docker build --platform linux/amd64 -t fitguard .
heroku container:push web -a fitguard-prod
heroku container:release web -a fitguard-prod

Heroku provides PORT and the add-on provides REDIS_URL. The container image's EXPOSE line is not the port configuration. Check https://<app>.herokuapp.com/healthz.

Railway

In your project choose New → Docker Image and enter ghcr.io/oluiy/fitguard:latest. Add FITGUARD_CONFIG and your provider keys under Variables, generate a public domain, and set the health check to /healthz. Railway can pull a public GHCR image directly; a private one needs their Pro plan, which is why the FitGuard package is public.

Attach a Railway Volume mounted at /data and set data_dir: /data if SQLite history must survive. Railway volumes cannot be used with replicas. For multiple replicas, use Redis for budget and cache state and treat SQLite dashboards as per-instance.

Data rule: Redis does not store FitGuard's request history. It coordinates budget/cache state; SQLite history needs a persistent disk or an external logging design.
